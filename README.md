# SocialSphere Analytics Platform

**Large-Scale Product Analytics Data Warehouse**

A production-style analytics platform that ingests simulated social-media product events, stores them in a Bronze/Silver/Gold data lake, transforms them with PySpark, and serves product KPIs through a Streamlit dashboard — the same pattern companies like Meta, Netflix, and Airbnb use internally to track product behavior.

> **Data is synthetic.** Every event is generated by `event_generator/`. No real user data is collected, stored, or processed anywhere in this project.

---

## Overview

SocialSphere answers questions like:
- How many daily/weekly/monthly active users do we have, and how sticky is engagement?
- Where do users drop off in the signup → engagement → subscription funnel?
- What's our Day 1 / Day 7 / Day 30 retention?
- Which features drive the most usage?
- What's our revenue, ARPU, and subscription trend?
- Are there unusual spikes or drops in traffic or revenue?

## Problem Statement

Product teams at consumer-scale companies need a reliable, queryable record of *what users actually did* — not just raw logs, but clean, business-ready metrics they can trust day over day. This project builds that pipeline end-to-end: ingestion → validation → transformation → analytics tables → dashboard, with data quality checks at each handoff so a broken upstream system fails loudly instead of silently corrupting a KPI dashboard.

## Architecture

```
Synthetic Event Generator
        |
        v
FastAPI Event Ingestion Service  (Pydantic-validated)
        |
        v
Bronze Layer (MinIO/S3, partitioned by year/month/day/hour)
        |
        v
Airflow DAG (daily_product_analytics_dag)
        |
        v
PySpark: Bronze -> Silver  (dedup, validate, standardize)
        |
        v
Silver Layer (Parquet, partitioned by event_date)
        |
        v
PySpark Gold Jobs (run in parallel): daily metrics, retention,
funnel, feature usage, revenue, anomaly detection
        |
        v
Gold Layer (6 business-ready Parquet tables)
        |
        v
Streamlit Dashboard (6 pages)
```

## Key Features

- **Synthetic event generator** with realistic user behavior: churn propensity, signup-date-weighted activity, session patterns, and ~1-2% intentionally corrupted records for data-quality testing
- **FastAPI ingestion service** with full Pydantic schema validation, single and batch endpoints, buffered writes to MinIO
- **7 PySpark jobs**: bronze→silver cleaning + 6 gold-layer analytics jobs (daily metrics, retention cohorts, funnel, feature usage, revenue, anomaly detection)
- **3 Airflow DAGs**: daily orchestration (with parallel task execution), standalone data-quality monitoring, and manual backfill
- **Data quality framework**: 7 automated checks (null IDs, duplicates, valid event types, future timestamps, negative revenue, volume drops, partition completeness)
- **6-page Streamlit dashboard**: Product KPIs, Retention (with cohort heatmap), Funnel Analysis, Feature Usage, Revenue, Anomaly Detection
- **27 passing unit/integration tests**, including a regression test for a real funnel-logic bug caught during development

## Data Pipeline

| Stage | Tool | Input | Output |
|---|---|---|---|
| Generate | `event_generator/generate_events.py` | — | Partitioned NDJSON |
| Ingest | `ingestion_service/main.py` | HTTP POST | MinIO bronze objects |
| Clean | `spark_jobs/bronze_to_silver.py` | Bronze NDJSON | Silver Parquet |
| Aggregate | `spark_jobs/*_job.py` (6 jobs) | Silver Parquet | Gold Parquet (6 tables) |
| Orchestrate | `airflow/dags/*.py` (3 DAGs) | — | Runs the above on a schedule |
| Serve | `dashboard/app.py` + 6 pages | Gold Parquet | Interactive dashboard |

## How to Run Locally

### Option A: Quick local run (no Docker)

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Generate synthetic data (adjust --events for scale)
cd event_generator
python generate_events.py --events 100000 --users 5000 --output ../data/bronze_local
cd ..

# 3. Run the full Spark pipeline (or use `make pipeline-local`)
make pipeline-local

# 4. Run data quality checks
cd data_quality && python validation_rules.py --silver-path ../data/silver_local && cd ..

# 5. Launch the dashboard
make dashboard
# -> http://localhost:8501
```

### Option B: Full Docker Compose stack

```bash
cp .env.example .env
docker-compose up -d minio minio-init postgres
docker-compose up -d ingestion_service
# generate + load data into MinIO, then:
docker-compose up -d airflow-init airflow-webserver airflow-scheduler
docker-compose up -d dashboard
```

- Ingestion API: http://localhost:8000/docs
- Airflow UI: http://localhost:8080 (admin/admin)
- MinIO console: http://localhost:9001
- Dashboard: http://localhost:8501

### Scaling up

```bash
python event_generator/generate_events.py --events 5000000 --users 200000 --output ./data/bronze_local
```

## Data Quality Checks

`data_quality/validation_rules.py` (full check suite) plus focused subsets in `schema_checks.py` and `freshness_checks.py`:

- No null/empty `event_id`
- No duplicate `event_id`
- Only recognized `event_type` values
- No future `event_timestamp`
- No negative `revenue`
- Event volume hasn't dropped >50% vs. trailing 7-day average
- Expected partitions exist in the silver table

## Performance Optimizations

- **Partition pruning**: silver and gold tables are partitioned by `event_date`, so date-range queries only scan relevant partitions
- **Range-join instead of cross-join for WAU/MAU**: the rolling 7/30-day active-user windows are computed with a date-range join predicate rather than a full cross join between dates and users — found during scale testing (a cross join was fine at test-data size but stalled at ~50K users / ~1M events); fixed and re-verified against the same expected output (see `docs/pipeline_design.md`)
- **Parallel DAG execution**: 4 of the 6 gold jobs have no inter-dependencies and run concurrently in Airflow
- **Buffered ingestion writes**: the FastAPI service batches events in memory (flush at 500 events or 10s, whichever first) instead of writing one object per event
- **Cached dashboard reads**: Streamlit's `@st.cache_data(ttl=300)` avoids re-reading Parquet on every UI interaction
